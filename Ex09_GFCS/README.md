# Ex09: GFCS — конверсія розрідженої мережі у компактну щільну архітектуру

Відповідає підрозділу **§2.4** дисертації («Методи конверсії розріджених мереж у компактні
щільні архітектури»).

## Мета

Розріджена (pruned) мережа зберігає нульові ваги у пам'яті — фізичний розмір моделі не
зменшується. Ex09 розв'язує задачу конверсії: за розрідженою мережею f_S = θ ⊙ M
побудувати компактну щільну мережу f_C меншого фізичного розміру, що зберігає якість
(§2.4.1 — формалізація без доступу до даних). **GFCS (Gradient-Flow Connectivity Synthesis)**
— авторський метод конверсії: двонаправлена потокова метрика важливості нейронів
(§2.4.2, `ex09_lib/gfcs.py`) і жадібне злиття функціонально надлишкових нейронів.

**Гіпотеза:** GFCS дає позитивну зміну якості відносно розрідженої моделі-донора при
суттєвому стисненні параметрів, без доступу до тренувальних даних під час самої конверсії.

## Чесний опис протоколу

- **ΔF1 виміряно відносно розрідженої моделі, не вчителя**: `delta_f1 = final_f1 − sparse_f1`
  (`ex09_full_benchmark.py:205`). Це показує виграш конверсії над станом "щойно
  проріджено", а не абсолютну якість щодо повної моделі (для цього є окреме поле
  `recovery = final_f1 / teacher_f1`).
- **Уніфіковане донавчання для всіх методів**: після конверсії кожен з 6 методів
  проходить однакове донавчання **10 епох**, `lr=0.01`, SGD
  (`ex09_full_benchmark.py:99–101, 191–193`, `do_finetune(compact, train_dl, epochs=10, ...)`).
  Порівняння методів — це порівняння результату конверсія+донавчання, а не самої лише
  конверсії.
- **RCU вимірює лише конверсію, не донавчання**: поле `rcu_conversion` профілюється
  окремим викликом `profile_rcu(do_conversion, ...)` до донавчання
  (`ex09_full_benchmark.py:182–185`); `rcu_total = rcu_conversion + rcu_finetune`
  включає й донавчання. У таблицях звітів "RCU" за замовчуванням означає
  `rcu_conversion` — це вартість самого перетворення розрідженої мережі в компактну,
  без вартості подальшого тренування.
- RCU (Relative Compute Units) — апаратно-незалежна метрика: `thread_time(алгоритм) /
  thread_time(еталонний обчислювальний блок)`, див. `ex09_full_benchmark.py:34–75`.

## Додаткові порівняння

- **`results/structured_vs_gfcs.json`** (`ex09_structured_vs_gfcs.py`) — конвеєр
  «неструктуроване проріджування + GFCS» проти двох SOTA-методів структурного
  проріджування (Taylor, Network Slimming) на однаковому цільовому стисненні. GFCS
  програє в коефіцієнті стиснення при однаковій розрідженості (структуровані методи
  прибирають цілі нейрони одразу), але вигідно поєднується з неструктурованим
  проріджуванням там, де воно вже застосовується. Не цитується в основному тексті
  дисертації; наведено як контекст для §2.5 (обмеження).
- **`results/multi_arch_benchmark.json`** (`ex09_multi_arch.py`) — те саме порівняння на
  4 архітектурах MLP різної ширини/глибини (SimpleMLP, DeepMLP, WideMLP,
  BottleneckMLP). Показує, що перевага GFCS зростає з шириною мережі (0/4 перемоги на
  128 нейронів → 3/4 на 256).

## Обмеження

- Основний бенчмарк (§2.4.4) — 2 seeds на датасет; статистична потужність обмежена.
- Метод перевірено лише на MLP-архітектурах у §2.4.4; верифікація на CNN/ResNet
  (§2.4.5) — 2 повтори, попередня оцінка масштабованості, не остаточний доказ.
- RCU конверсії GFCS (≈80 RCU у середньому) суттєво дорожчий за NeuronRemoval (≈0,09)
  та WeightRedist (≈0,08) — вартість еволюційного пошуку архітектури.
- Структуровані методи проріджування (Taylor, Network Slimming) дають більший
  коефіцієнт стиснення за тієї самої розрідженості, ніж конвеєр «неструктуроване
  проріджування + GFCS» (`results/structured_vs_gfcs.json`).
